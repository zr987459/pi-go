# V2 独立评审：pi-go 三份提案

- 评审人：V2（没有读 docs/votes/ 下的其他投票）
- 日期：2026-11-03
- 核实依据：
  - pimet@a80222c2dda4a4c8a936258b96597bc7ea7d4102 源码
  - npm `@earendil-works/pi-coding-agent@1.5.0` 包内的 `dist/modes/rpc/rpc-types.d.ts`、`docs/{rpc,rpc-commands,rpc-extension-ui,json,message-types,session-format,providers,models-configuration,cli,environment-variables}.md`、`CHANGELOG.md`
  - npm 上 `@mariozechner/pi-coding-agent` 的元数据
  - IPF-Sinon/DSH-Folk 的 `TarGzipExtractor.java`（逐行比对）
  - dsh-Go 仓库元数据（确认 AGPL-3.0）

## 一、总评

| 方案 | 总分 | 复用/迁移风险 | pi 接口真实性 | MVP 真机可行 | 并行拆分 | 许可证 | 新手可用性 |
|---|---|---|---|---|---|---|---|
| A | **7.5** | 7 | 8.5 | 8 | 6.5 | 5 | 8 |
| **B** | **8.5** | 8.5 | 9.5 | 8 | 7 | 9.5 | 7.5 |
| C | **7.0** | 6.5 | 9 | 6 | 8.5 | 4.5 | 7.5 |

三份提案的大方向一致：都选 Kotlin + Compose，都通过 `pi --mode rpc` 走 stdin/stdout JSONL，都用 `@earendil-works/pi-coding-agent` 并锁定 1.5.0，都从 PiMet 迁移 PRoot 和国内镜像现装。
真正拉开差距的是三件事：**PiMet 里有没有别人的 GPL 代码**、**MVP 范围**、**工作流在 `app/` 装配层的边界**。
B 是唯一发现并处理 PiMet 中 GPL-3.0 派生代码的方案（我已独立复核，见 §三.1）。它的协议描述在三份里也最准确，所以投 B。

## 二、逐个方案

### 方案 A（7.5）

优点
- 落地细节最扎实：Ubuntu Base 用 `SHA256SUMS` 校验，Node 用 `SHASUMS256.txt` 校验；换镜像时删掉 `.part` 再下（修掉 PiMet 把不同来源拼进同一个文件的 bug）；先解压到 `staging/` 再原子重命名；删除会话先进回收目录；停进程只杀自己的进程树，不再 `pkill node`。这些都直接对应 REVIEW.md 的必报项。
- 协议层面写对了几处关键点：
  - 生成中的状态以 `agent_settled` 为准；
  - `parse` 错误不带 id；
  - `prompt` 成功只代表被接受；
  - `abort` 不清空队列；
  - 对话类扩展请求必须应答。
- 启动参数加了 `PI_OFFLINE`、`PI_SKIP_VERSION_CHECK`、`PI_TELEMETRY=0`，能减少 PRoot 下的冷启动网络等待。三个变量在 `environment-variables.md` 里都有。
- 生成中按发送键默认是"排队"、长按才是"插话"。对新手来说最不容易出意外。
- 空间预检、启动失败按 stderr 归类成中文提示，对新手友好。

缺点
- **许可证漏洞**：计划原样迁移 `TarGzipExtractor.java`（§4.1），没有发现它和 DSH-Folk（GPL-3.0）的同名文件几乎逐行相同。原样搬进来，pi-go 就成了 GPL-3.0 衍生作品，和 §8 "pi-go 不受 copyleft 约束、可自选 Apache-2.0" 的结论矛盾。
- 并行边界有两处共享文件：
  - `THIRD_PARTY_NOTICES.md` 的"运行时部分"划给 runtime，其余部分归 scaffold，同一个文件两个人改；
  - `AppContainer` 改成真实实现，交给"最后合入的工作流"顺手做。这不是可审查的归属。
- `:core:rpc` 同时承担协议、会话扫描、`ProviderConfigStoreImpl`（写容器文件），职责偏重；`:feature:setup` 一个模块塞了向导、模型配置、会话列表、设置四块，工作量和 chat 不平衡。
- 计划用 AndroidX Security 加密存 Key。`security-crypto` 的 EncryptedSharedPreferences 已被 Google 弃用，建议直接用 Keystore + AES-GCM（C 的做法）。
- 不带 `--ignore-scripts` 的理由（"需要 postinstall 的依赖会装残"）在 1.5.0 上没有依据：pi 本体和直接依赖都没有 install 脚本。改动本身无害，但理由不成立。

### 方案 B（8.5）

优点
- **唯一做了许可证尽调的方案**，并给出可执行的对策：
  - 指出 PiMet 的 `TarGzipExtractor.java` 和 DSH-Folk 的同名文件 447/453 行一致（我复核结果相同：DSH-Folk 522 行，PiMet 453 行，其中 447 行匹配，相似度 0.917）；
  - 指出 `build-slim-rootfs.yml` 是从 DSH-Folk 的 release 下载 rootfs 后裁剪再分发（已复核：第 19、46 行）。
  - 对策：重写解压器（Commons Compress），用 Kotlin 重写 DNS 和用户组修复，不分发派生的 rootfs，再加一条 CI 检查 `me.bmax.apatch` 和片段哈希。
- 协议描述最完整、最准确：
  - 命令全集和 `rpc-types.d.ts` 一致；
  - 指出 `disposition:"handled"` 时不要等 `agent_settled`；
  - `new_session` 检查 `data.cancelled`；
  - `get_session_stats` 读的 `contextUsage.percent` 真实存在；
  - `auth.json` 写成 `{"<provider>":{"type":"api_key","key":…}}`，与 providers.md 一致；
  - 未知 role 渲染成原始 JSON，是 message-types.md 的要求。
- 迁移清单逐类写明"改 / 重写 / 原样搬 / 不搬"，迁移风险可控。`libproroot*.so`（我已确认 PiMet 的 Java 代码没有引用）和 doro/elaina 素材都明确不带。
- 只在运行中持有 WakeLock（`agent_start` 到 `agent_settled`），比 PiMet 常驻省电；`abort` 20 秒不应答就强杀并用 `--session` 恢复，兜底清楚。
- 跨 cwd 打开会话时重启进程、同 cwd 用 `switch_session`。这正确处理了"cwd 决定会话目录和 AGENTS.md"这一点，A 和 C 都没说清楚。
- pi 升级有兼容范围（`>=1.5.0 <2.0.0`），失败自动回滚旧版本；"重置运行环境"保留 `root/.pi/agent`。

缺点
- **装配层没有归属**：`app/**` 全归 W0，`AppGraph` 默认绑定 Fake 实现。W1 到 W4 合入后，由谁、在哪个分支把 `AppGraph` 切到真实实现，没有写。要么最后集成时越界改 `app/`，要么一直跑 Fake。
- 运行中的主按钮默认是"插话"（steer）。新手容易在工具执行中途改变模型方向而不自知；A 默认"排队"更稳。
- `NODE_OPTIONS=--max-old-space-size=512`：长会话、`get_messages` 带大量工具输出时有 OOM 风险。建议改成 768–1024 或按设备内存决定，并在崩溃诊断里识别 heap OOM。
- 仍然用 `--ignore-scripts`，A 和 C 也一样；1.5.0 下没问题，但升级 pi 时要复查依赖有没有 install 脚本。
- 重写解压器会给 W1 增加真实工作量（绝对符号链接、硬链接、PAX 等边角），MVP 工期要计入。
- 事实性错误见 §三.2。

### 方案 C（7.0）

优点
- **并行拆分最干净**：`app/di/{Runtime,Agent,Data,Chat}Bindings.kt` 每个文件只归一条工作流，`PiGoService` 明确由 W3 接管；共享的 `libs.versions.toml` / `settings.gradle.kts` 只能由 scaffold 改，再单独加一条 `mvp/integration` 分支只切 Bindings。三份里只有它真正解决了 `app/` 装配层的冲突。
- **Key 安全最好**：内置 Provider 的 Key 用环境变量注入；`models.json` 里写 `"$PIGO_KEY_<name>"`，`models-configuration.md` 明确支持 `$NAME` 插值；Key 用 Android Keystore 加密，容器磁盘上不落明文。这弥补了 pi 的 bash 工具能读到 `auth.json` 的问题（B 的 R6 也注意到了，但留到二期）。
- 安装 pi 到带版本号的 prefix，`/usr/local/bin/pi` 软链到 `current`，冒烟通过（`--version` + RPC 握手 + `get_available_models`）后再切换，回滚最可靠。
- 验收里明确要有国产 ROM 真机、Android 12+ 幻影进程限制的对策，贴近国内用户实际。
- Provider 环境变量名以 providers.md 为准（`DEEPSEEK_API_KEY`、`MINIMAX_CN_API_KEY`、`ZAI_CODING_CN_API_KEY` 都对）。

缺点
- **许可证漏洞，而且比 A 更重**：
  - `TarGzipExtractor` 写明"原样搬（仅改包名）"；
  - rootfs 路线 A "一期可读 PiMet 的 `runtime-latest` 发布物"，而那个发布物正是 DSH-Folk rootfs 的裁剪再分发；
  - 迁移表把 `libproroot*.so` 列进"原样搬"，又在同一行说"核实前不打包"，自相矛盾。
- **MVP 过大**：一期就要图片附件、平板/横屏双栏、`edit` diff、排队消息"立即发送"（靠 clear_queue 再全部重发来模拟，容易出现重复或丢失，恰是 REVIEW.md 的必报项）、9 家 Provider、冷启动 ≤ 3 秒。PRoot 下 Node 冷启动通常要数秒，≤ 3 秒只能靠"先显示输入框、后台启动"满足，验收口径含糊。真机走通的风险最高。
- `ChatRepository` 接口定义在 `:feature:chat` 一节，实现却在 W3 的 `core/agent`。如果接口放在 feature 模块，就违反了它自己写的"core 不依赖 feature"方向；文中没说接口放在哪个 core 模块。
- 启动参数写 `-e /root/.pi-go/ext/*.ts`：ProcessBuilder 不经过 shell，通配符不会展开，需要逐个文件传，或者放进 `~/.pi/agent/extensions/` 让 pi 自动发现。

## 三、事实性错误与需要更正的地方

### 1. 三份共同或会影响最终稿的
1. **PiMet 含 GPL-3.0 派生代码**（A、C 漏掉，B 指出）：
   - `app/src/main/java/com/xm486/pimet/proot/TarGzipExtractor.java` 和 `IPF-Sinon/DSH-Folk:app/src/main/java/me/bmax/apatch/dsh/TarGzipExtractor.java` 比对：447/453 行相同；DSH-Folk 是 GPL-3.0（GitHub API 确认）；
   - `ProotManager.java` 第 38、740、909 行注释写着"参考 DSH-Folk / DSHA"；
   - `.github/workflows/build-slim-rootfs.yml` 第 19、46 行从 DSH-Folk 的 release 下载 rootfs。
2. **国内 Provider 预设的名字会误导用户**：pi 1.5.0 内置的"智谱 / 通义 / Kimi"实际是套餐专用端点：`ZAI Coding Plan`（`ZAI_CODING_CN_API_KEY`）、`Qwen Token Plan`（`QWEN_TOKEN_PLAN(_CN)_API_KEY`）、`Kimi For Coding`（`KIMI_API_KEY`）。普通的智谱开放平台 / 百炼 DashScope Key 填进去会失败。A 写"通义千问、智谱、Kimi"，B 写"Qwen（China）、ZAI（China）"，C 写"Qwen、智谱 ZAI（中国）"，都没说明这一点。最终稿应该把预设拆成"编程套餐（内置）"和"按量 API（走自定义 OpenAI 兼容端点，预填 baseUrl）"两类，界面文案写明"需要编程套餐 Key"。
3. 三份都说"RPC 没有列会话命令"，这是对的；会话路径的转义规则（去掉开头 `/`，把 `/ \ :` 换成 `-`）也和 session-format.md 一致。
4. `steer` / `follow_up` 命令本身也接受 `images` 字段（`rpc-types.d.ts`），三份都只在 `prompt` 上提到图片。不影响 MVP。

### 2. 方案 A
- "1.5.0 起 `message_update` 去掉累计快照、只发 delta"：不准确。CHANGELOG 显示这是 **0.84.0（2026-08-06）** 的改动。
- "1.5.0 每写一条记录都等 stdout 背压"：背压在 **0.76.0** 就有了。两处对锁定 1.5.0 的实现没有影响，但"以 1.5.0 源码为准"的说法应当改正。
- `tool_execution_start` 的 `parentToolCallId?`：只在工具嵌套调用另一个工具时出现（extensions.md），json.md 的事件表里没有。可选字段，写法没问题，但应注明来源。
- `partialResult` "bash 的本身是累计的，要替换"：json.md 原文是"替换还是追加取决于工具的结果约定"。对内置 bash 来说替换是对的，但不应该当作通用规则。

### 3. 方案 B
- §4.8"App 被系统杀，冷启动后若最后一条 assistant 的 `stopReason=="pending"`，显示'中断'"：**这个检测不可能成立**。message-types.md 写明 pi **不会**把 `"pending"` 的 assistant 消息写进会话 JSONL，所以 `get_messages` 里看不到。应改成：最后一条是 user 消息、后面没有 assistant 回复（或 App 自己在 DataStore 记了"运行中"标记），就视为中断。
- §1.3 写"四种对外接口"，后面实际列了五种（TUI、print、json、rpc、SDK）。笔误。
- R10 "必要时启动参数加 `--no-approve`"：`-na/--no-approve` 的作用是**忽略**需要信任的项目本地文件，不是"自动同意"。写法没错，但要说清它会让项目里的 `.pi/` 扩展和技能不加载。

### 4. 方案 C
- 把 PiMet 的 `runtime-latest` rootfs 当作"预制精简 rootfs"直接用：来源是 DSH-Folk 的发布物，二次分发授权不明（见 §三.1）。
- `-e /root/.pi-go/ext/*.ts`：通配符不会展开（见上）。
- 迁移表里 `libproroot*.so` 的处理前后矛盾（见上）。
- "PiMet 设备版本也已安装新包名"属实（`PiWebManager.java:113`），但 PiMet 同时装了 `@agegr/pi-web`，它内部引用旧版 pi-coding-agent（`ProotManager.java:221` 起的兼容补丁）。迁移时要确认 pi-go 的容器里不再装 pi-web，避免同一个 rootfs 里有两个 pi 版本。

### 5. 已核实无误的关键事实（三份共同）
- `@mariozechner/pi-coding-agent` 最新版 0.73.1，已标 deprecated（"please use @earendil-works/pi-coding-agent"）；`@earendil-works/pi-coding-agent` 的 latest 是 1.5.0，`engines.node >=22.19.0`，MIT。
- `agent_settled{aborted}`、`queue_update{steering,followUp}`（每次都是完整队列）、`tool_execution_end.durationMs`、`prompt.streamingBehavior`（生成中不带就报错）、`clear_queue` 先于 `abort`（官方 Esc 推荐做法）、`extension_ui_response` 用 `value` / `confirmed` / `cancelled`、`editor` 没有 timeout、只按 `\n` 切行，不要用把 U+2028 当换行的读取器：都和文档一致。
- PiMet：77 个 Java 文件、约 5.16 万行、0 个 Kotlin；targetSdk 28；没有 LICENSE；jniLibs 里有 5 个 `libproroot*.so`，Java 代码没有引用；`assets/pets` 下有 doro、elaina-2。

## 四、最终稿应从其他方案吸收的具体优点（以 B 为底）

1. **从 C 吸收装配层拆分**：`app/di/RuntimeBindings.kt`、`EngineBindings.kt`、`StoreBindings.kt`、`ChatBindings.kt` 每个文件归一条工作流，加 `mvp/integration` 分支只切 Bindings；`libs.versions.toml` / `settings.gradle.kts` 只归 scaffold。这样补上 B 的装配缺口。
2. **从 C 吸收 Key 不落容器明文**：内置 Provider 用环境变量注入，自定义端点在 `models.json` 写 `"$PIGO_KEY_<id>"`，Key 存 Android Keystore（AES-GCM）。B 的 R6 应该提前到 MVP。
3. **从 C 吸收带版本号的 prefix + `current` 软链做 pi 升级回滚**，冒烟加一次 `get_available_models`。
4. **从 A 吸收下载完整性与数据安全细节**：Ubuntu / Node 做 SHA256 校验；换镜像时删 `.part`；解压到 `staging/` 再原子重命名；删除会话进回收目录（B 现在是直接删文件）；可用空间预检；启动失败按 stderr 归类成中文提示。
5. **从 A 吸收新手默认值**：生成中发送默认"排队"（follow_up），插话放在长按或次要按钮；停止键在输入框为空时出现，`clear_queue` 拿回的文本不覆盖用户正在写的新草稿。
6. **从 A 吸收冷启动环境变量**：`PI_OFFLINE=1`、`PI_SKIP_VERSION_CHECK=1`、`PI_TELEMETRY=0`。
7. **从 C 吸收验收口径**：至少一台国产 ROM 真机；写明 Android 12+ 幻影进程的处理和电池白名单引导。但 C 的图片、双栏、diff、"立即发送"都推到二期。
8. 新增（三份都缺）：Provider 预设拆成"编程套餐（内置 Provider）"和"按量 API（自定义 OpenAI 兼容端点，预填 DeepSeek / 百炼 / 智谱开放平台 / Moonshot 的 baseUrl）"，避免新手填错 Key 类型。
9. B 的冷启动"中断检测"改成"最后一条是 user 消息、后面没有 assistant 回复"，或者 App 自己在 DataStore 记运行标记。

## 五、投票理由（一句话）

B 的协议细节最贴近 pi 1.5.0 的真实接口，也是唯一识别并规避了 PiMet 里 GPL-3.0 派生代码的方案。它的主要缺口（装配层归属、Key 落盘、新手默认值）都能用 C 和 A 的具体做法补上；反过来，A 和 C 的许可证问题在架构层面就要返工。
