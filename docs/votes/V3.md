## 2. 各方案优缺点

### 方案 A（= 当前 `docs/DESIGN.md`）—— 7.3 分

优点
- 协议章节写得最“可直接开工”：命令/响应/事件三张表与 `rpc-types.d.ts` 基本一一对上（`get_state` 的 12 个字段、`prompt.streamingBehavior`、`clear_queue` 返回 `steering/followUp`、`extension_ui_response` 三种形态都正确）。
- 抓住了 RPC 的几个坑：只按 `\n` 分帧、不能用会切 U+2028 的读取器、`parse` 错误没有 id、`agent_end` ≠ 空闲要等 `agent_settled`、`editor` 对话框无超时必须应答、未实现的 method 立即回 `cancelled`。
- 运行环境改进最务实：**Ubuntu 用 `SHA256SUMS`、Node 用 `SHASUMS256.txt` 校验**（PiMet 确实完全没有校验，我 grep 过 `MessageDigest`/`sha256` 为 0）、换镜像删 `.part`、解压到 `staging/` 再原子改名、空间不足预检、**只杀自己启动的进程树**（PiMet `PiWebManager` 里确有 `pkill -9 -f node`）。
- 会话删除进 `sessions-trash/`，符合 REVIEW.md“删除会话没进回收目录 = Important”。
- 启动环境用了真实存在的 `PI_OFFLINE`、`PI_SKIP_VERSION_CHECK`、`PI_TELEMETRY`，能缩短 PRoot 下冷启动。
- 新手体验细：Key 粘贴自动去空格和 `Bearer ` 前缀、错误归类成中文一句话、返回键行为写进验收。

缺点
- **许可证漏判（Important）**：计划把 `TarGzipExtractor.java` + `SafeFiles.java` “原样搬”。我逐行比对：PiMet 的 `TarGzipExtractor.java`（453 行）与 DSH-Folk 同名文件有 **447 行完全一致（相似度 0.917）**，DSH-Folk 是 **GPL-3.0**；`ProotManager.java:38`、`:740`、`:909` 注释也明写“参考 DSH-Folk / DSHA”。A 又建议 pi-go 可以选 Apache-2.0——若照做就是违规。
- **模块归属矛盾（Important）**：`ProviderConfigStoreImpl` 放在“纯 Kotlin/JVM”的 `:core:rpc`，却要求“Key 改存 AndroidX Security 加密存储”。纯 JVM 模块无法依赖 AndroidX Security / Keystore，scaffold 落地时就会卡住，要么改模块类型、要么把实现挪走，都会改动别的工作流范围。
- Key 最终仍以明文写进容器 `auth.json`（pi 的 bash 工具可读），没提 pi 支持的 `$VAR` / `!command` 引用。
- 工作目录写死 `/root/workspace`，不同 cwd 的会话没说怎么打开（`switch_session` 跨 cwd 的行为未处理）。
- `THIRD_PARTY_NOTICES.md` 被 runtime 工作流“改运行时部分”，但其他工作流引入依赖也要改同一文件 → 实际共享文件。
- 几处事实小错见 §4。

### 方案 B —— 8.6 分

优点
- **唯一做了许可证尽调并给出可执行对策**：TarGzipExtractor 与 DSH-Folk 447/453 行一致（我复核结果相同）、`ProotManager` 的 DSH-Folk 注释、PiMet `runtime-latest` rootfs 来自 DSH-Folk release 的二次分发；对策是用 Commons Compress 重写解压、从零写 DNS/组文件修复、弃用派生 rootfs，并加 CI 检查 `me.bmax.apatch` 片段。这让 pi-go 真正能自选许可证。
- 复用清单粒度最细且全部属实：我核对了它列出的 `buildProotProcess / getRootfsDir / getTmpDir / getNativeLibDir / isNativeProotAvailable / headOk / downloadFromAny / testUrlRealThroughput / testAndSortCandidateUrls / downloadWithResume / buildDomesticRootfs / writeDomesticAptConfig / latestNodeV24` 等方法，PiMet 里全都存在；`buildProotProcess` 参数（含 `-b /dev/urandom:/dev/random`、`/root/shared`、`env -u LD_LIBRARY_PATH`）、`PI_CODING_AGENT_DIR=/root/.pi/agent`、`/root/pi-cwd`、`--ignore-scripts` 安装命令都与源码一致。
- 协议最完整：RPC 命令全集与 `rpc-types.d.ts` 完全一致；`disposition=handled` 不等 `agent_settled`、`new_session.data.cancelled`、`auto_retry_end.finalError`、`get_session_stats.contextUsage.percent`、`message_end.stopReason` 的 `length`/`aborted`/`error` 分支、历史重建时 `toolCall` 与 `toolResult` 按 `toolCallId` 合并、未知 role 渲染原始 JSON——都有文档依据。
- 处理了跨 cwd 会话：同 cwd 用 `switch_session`，不同 cwd 以 `--session <path>` 重启进程，这是 A/C 都没想清楚的点。
- 工程判断好：WakeLock 只在 `agent_start…agent_settled` 间持有（PiMet 是常驻 WakeLock）；`abort` 20s 不应答强杀并以 `--session` 恢复；`queue_update` 为唯一真相，不在客户端自建队列；pi 升级失败自动回滚。
- 工作流边界清楚：W0 先放好所有 `api/` 接口和 Fake，W1–W4 各占模块目录；W2 可用桌面 Linux 上的真 pi 做集成测试，不依赖手机。

缺点
- **没有下载完整性校验（Important）**：Ubuntu/Node 包下载后没有 SHA256 校验，REVIEW.md 把“下载或解压没有校验就使用”列为必须报。A 已有现成做法。
- **会话直接删除（Important）**：L4 “文件被删除”，违反 REVIEW.md“删除会话没进回收目录”。
- Key 明文写容器 `auth.json`（自己在 R6 承认，二期才考虑 `!cmd`）；对新手的风险提示只是一句话。
- 没写谁把 `AppGraph` 从 Fake 切到真实实现（`app/**` 全归 W0）；`jniLibs` 归 W0 但 `core/runtime/src/main/**` 又归 W1，存在路径重叠。
- 预设供应商名不准，会让新手选错（见 §4）。
- `NODE_OPTIONS=--max-old-space-size=512` 对大仓库任务偏紧，建议可配。

### 方案 C —— 6.9 分

优点
- **Key 处理最安全**：内置供应商用环境变量（`DEEPSEEK_API_KEY`、`MOONSHOT_API_KEY`、`MINIMAX_CN_API_KEY`、`ZAI_CODING_CN_API_KEY` 均在 `providers.md` 中真实存在）注入，自定义端点在 `models.json` 写 `$PIGO_KEY_<name>`（`$NAME` 插值是 `models.json` 支持的语法），**明文 Key 不落容器磁盘**，Key 用 Keystore AES-GCM 存宿主。
- `AppGraph` 拆成 `di/RuntimeBindings.kt / AgentBindings.kt / DataBindings.kt / ChatBindings.kt`，每个文件归一个工作流，是三份里解决“装配文件冲突”最好的做法；还有独立 `mvp/integration` 切换步骤。
- pi 装到 `/opt/pi-go/pi/<版本>` + `current` 软链，升级“装新 prefix → 冒烟 → 切软链”，回滚最干净；验证阶段用 `pi --mode rpc --no-session` 发 `get_state` 做 RPC 握手。
- 风险表最贴近真机：Android 12+ 幻影进程限制、国产 ROM 杀后台，并要求验收设备含一台国产 ROM。
- 对 dsh-Go 的描述最准确（引擎是 DeepSeek Harness，不是 pi）。

缺点
- **许可证漏判（Important）**：与 A 一样计划“原样搬” `TarGzipExtractor`；而且路线 A 的快速安装直接读 PiMet `runtime-latest` rootfs——B 指出这是 DSH-Folk 派生包，C 只当“跨仓库耦合”处理，没有意识到许可证问题。
- **没有下载完整性校验、会话直接删除**（同 B 的两条 Important）。
- **MVP 范围过大**，真机走通风险最高：一期就要做图片附件、平板/横屏双栏、`edit` diff、排队消息“立即发送”（需要 `clear_queue` 后按序重发，易丢/重）、两条 rootfs 路线、带回滚的多版本 pi、冷启动 ≤3s。这些都不是用户要求的 MVP 必需项。
- 依赖方向不自洽：`AgentHost`（`:core:agent`）启动时要用 `ModelConfig.buildEnv()`（`:core:data`），但声明的依赖图里 agent 与 data 是平级，没说谁依赖谁。
- W4（chat）开发依赖“W3 提供的夹具回放”，并行度打折扣。
- 启动参数 `-e /root/.pi-go/ext/*.ts` 用了 shell 通配符，`ProcessBuilder` 直接 exec 不会展开。
- Shizuku API 许可证写成 Apache-2.0，实际是 MIT（见 §4）。

## 3. 最终稿应从其他方案吸收的具体优点（以 B 为底稿）

从 A 吸收
1. **下载完整性**：Ubuntu Base 用同目录 `SHA256SUMS`、Node 用 `SHASUMS256.txt` 校验；校验失败删除并换镜像；换镜像时删 `.part` 不拼接；解压到 `staging/` 后原子改名；可用空间预检（B 写 2.5GB，按 A 取 3GB 更稳）。
2. **会话删除进回收目录** `~/.pi/agent/sessions-trash/`（可恢复）；删除当前会话前先 `new_session`。
3. 启动环境加 `PI_OFFLINE=1 PI_SKIP_VERSION_CHECK=1 PI_TELEMETRY=0`（注意 `PI_OFFLINE` 会关掉模型目录刷新，设置页“刷新模型列表”时需临时不带它）。
4. 扩展对话框兜底：未实现的 method 立即回 `{"cancelled":true}`，绝不让 pi 挂起。
5. 停止进程只杀自己启动的进程树，明确禁止 `pkill node`。
6. 新手细节：Key 粘贴自动去空格/`Bearer `、错误归类成中文一句话、返回键行为（聊天页退后台不结束服务；向导中返回要确认）写进验收。
7. 停止时“拿回的排队文本不覆盖用户正在写的新草稿”。

从 C 吸收
1. **Key 不落容器磁盘**：内置供应商用环境变量注入；自定义端点 `models.json` 写 `"apiKey": "$PIGO_KEY_<id>"`；宿主侧 Keystore AES-GCM。这一条应替换 B 的“明文写 auth.json + 600 权限”。
2. **`AppGraph` 按工作流拆 `di/*Bindings.kt`**，并设 `mvp/integration` 只负责把 Fake 切到真实实现——补上 B 没写的装配归属。
3. pi 装到版本化 prefix + `current` 软链，升级冒烟后切换，保留最近 2 个版本。
4. 安装验证增加 `pi --mode rpc --no-session` + `get_state` 握手。
5. 风险与验收加入：Android 12+ 幻影进程限制说明、国产 ROM 电池/自启动引导、验收设备至少一台国产 ROM。

B 自身需修
- `jniLibs` 明确只归 W1（`core/runtime/src/main/jniLibs/`），W0 不放二进制，消除路径重叠。
- 预设供应商改用 pi 真实 provider id（见 §4.2）。
- `--max-old-space-size` 改为可配置，默认 768–1024。

### 4.3 核实为正确、无需修改的关键事实（供最终稿放心引用）
- 包名：`@earendil-works/pi-coding-agent` latest = 1.5.0，`engines.node >= 22.19.0`，bin `pi → dist/bundle/cli.js`，MIT；`@mariozechner/pi-coding-agent` latest 停在 0.73.1，npm deprecated 提示 “please use @earendil-works/pi-coding-agent instead going forward”。**背景里写的 `@mariozechner/pi-coding-agent` 已弃用，最终稿应统一用 `@earendil-works/*`**（三份都正确指出了这一点）。
- RPC 命令全集（B、C 列表）与 `rpc-types.d.ts` 的 `RpcCommand` 联合类型完全一致；`extension_ui_response` 单独定义。
- `prompt` 在流式中不带 `streamingBehavior` 会返回错误；`disposition ∈ started/queued/handled`；`steer`/`follow_up` 的 disposition 为 `handled/queued`。
- `abort` 等会话空闲后才响应，且**不清空队列**（`rpc-commands.md`：“abort continues queued messages when they remain”）；官方建议的 Esc 行为正是“先 `clear_queue` 再 `abort`”。
- 响应需按 id 关联（“Command handling is asynchronous”）；`parse` 错误无 id；关闭 stdin 是有序关闭方式。
- CLI：`--session <path|id>`、`--session-dir`、`--no-session`、`-e/--extension`、`-na/--no-approve`、`--model provider/id` 均存在。
- 环境变量：`PI_CODING_AGENT_DIR`、`PI_OFFLINE`、`PI_SKIP_VERSION_CHECK`、`PI_TELEMETRY` 均存在。
- 会话路径 `~/.pi/agent/sessions/--<path>--/<timestamp>_<id>.jsonl`，转义规则“去掉开头分隔符，`/ \ :` → `-`”；RPC 无列会话命令。
- `auth.json` 条目格式 `{"<provider>":{"type":"api_key","key":"…"}}`，`key` 支持 `!command`；`models.json` 的 `apiKey` 支持字面量、`$NAME`、`!command`，`api` 可为 `openai-completions` 等。
- PiMet：`targetSdk 28 / minSdk 26 / compileSdk 34`、`useLegacyPackaging = true`；jniLibs 中 `libproroot*.so` 5 个仅在 arm64 存在且代码未引用；PiMet 仓库无 LICENSE；桌宠素材 `doro.codex-pet`、`elaina-2` 存在且无授权说明。
