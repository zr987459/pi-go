# V1 独立评审（评审人：Hark，2026-11-03）

评审依据（本人亲自核实，未读 docs/votes/ 下其他投票）：
- 三份提案：`docs/proposals/A.md`、`B.md`、`C.md`（main @ cc9ac19）。
- pi 引擎：npm `@earendil-works/pi-coding-agent@1.5.0` 包内 `dist/modes/rpc/rpc-types.d.ts`、`dist/core/agent-session.d.ts`、`docs/*.md`、`CHANGELOG.md`。
- npm 注册表：`@mariozechner/pi-coding-agent` 最新 0.73.1，已标 deprecated（“please use @earendil-works/pi-coding-agent instead going forward”）；`@earendil-works/pi-coding-agent` latest = 1.5.0，`engines.node >=22.19.0`。
- PiMet `a80222c` 的 `proot/TarGzipExtractor.java`，与 IPF-Sinon/DSH-Folk（GitHub 标注 GPL-3.0）的 `me/bmax/apatch/dsh/TarGzipExtractor.java` 做了逐行比对。PiMet 根目录确认没有 LICENSE 文件。

## 总评

三份提案的主架构几乎一样：都是 Kotlin + Compose、`pi --mode rpc` 走 stdin/stdout JSONL、复用 PiMet 的 PRoot 和国内镜像现装、targetSdk 28、单 pi 进程，并且都改用 `@earendil-works` 包名。所以胜负不在路线，而在三点：迁移时有没有踩许可证雷、接口细节对不对、并行拆分能不能真正落地。

**B 是唯一发现 PiMet 里有 GPL-3.0 派生代码的提案。** 我核实属实：两个 `TarGzipExtractor.java` 去掉首尾空格后的行序列相似度为 0.917，PiMet 453 行里有 408 行在 DSH-Folk 版里原样出现。A 和 C 都打算“原样搬（只改包名）”，照做的话 pi-go 会成为 GPL-3.0 衍生作品。如果用户最后选 GPL-3.0，这不算违规，但 A、C 的许可证章节都没意识到这个约束。B 的接口描述同样准确，工作流边界清楚，MVP 范围适中，所以投 B。

### A（7.7）
优点：
- 协议部分写得最扎实。`get_state` 的字段与 `RpcSessionState` 完全一致；`abort` 不清空队列；生成中的 `prompt` 必须带 `streamingBehavior`；`parentToolCallId`；1.5.0 的 `message_update` 只发 delta；`PI_OFFLINE`、`PI_SKIP_VERSION_CHECK`、`PI_TELEMETRY`。这些都核实存在。
- 安装环节最严谨：下载 Ubuntu 和 Node 后校验 SHA256；换镜像时删掉 `.part` 重下，修掉了 PiMet 把不同镜像内容拼进同一文件的 bug；先检查可用空间；解压到 staging 再原子重命名。
- MVP 范围克制。F11 把错误映射成中文提示、F12 定义返回键行为，对新手最友好。
- 删除会话先移到 `sessions-trash`，可以恢复。
- 生成中默认“排队”、长按才“插话”，理由写清楚了（不改变当前这一轮）。

缺点：
- 把 `TarGzipExtractor`、`SafeFiles` 列为原样搬，没有发现它来自 GPL-3.0 代码（见下方“事实性错误”）。
- “`AppContainer` 由最后合入的工作流改一行 bind”：runtime、rpc、chat、setup 实际上都要改这一个文件，并不是真正互不重叠。
- `ProviderConfigStoreImpl` 和 `SessionIndexImpl` 放在 `:core:rpc`，但只有 setup 用，rpc 工作流的负担偏重。
- 在 `--ignore-scripts` 上与官方文档相反（见下方）。

### B（8.6）
优点：
- 唯一做了许可证溯源。点名 `TarGzipExtractor` 的 GPL 来源，列出 `ProotManager` 里疑似改写的段落、派生自 DSH-Folk 的 GitHub rootfs、来源不明的 `libproroot*.so` 和桌宠素材，并给出“重写清单 + CI 禁止 `me.bmax.apatch`”的落地办法。
- 类级迁移表最细，每个 PiMet 类都标了搬、改、重写或不搬。
- RPC 细节准确：命令全集与 `rpc-types.d.ts` 一致；`new_session` 的 `data.cancelled`；`disposition=handled` 时不等 `agent_settled`；`contextUsage.percent`；`!command` 形式的 key；auth、models、settings 三个 json 的写法也都对得上文档。
- 只在 `agent_start` 到 `agent_settled` 之间持有 WakeLock。会话扫描只读文件头尾各 64KB。未知 role 渲染为原始 JSON。工程上都很务实。
- 工作流按模块切。W0 拥有各模块的 `api/` 包，其余工作流拥有模块里除 `api/` 外的部分，文件不重叠。

缺点：
- `AppGraph`（`:app`）由 W0 拥有，但没写谁、在哪一步把 Fake 换成真实实现，集成步骤缺失。应采用 C 的按工作流拆 Bindings 文件。
- 用 Apache Commons Compress 加 xz-java 重写解压，会多出依赖和工作量；W1 的工作量最大，也最容易拖期。
- 崩溃恢复用 `stopReason=="pending"` 判断（见下方错误）。
- 会话删除直接删文件，不如 A 的回收目录安全。

### C（7.3）
优点：
- `app/di/{Runtime,Agent,Data,Chat}Bindings.kt` 每个文件归一个工作流，是三份里最好的“集成点不重叠”设计。
- Key 安全性最好：Keystore 加密，启动时用环境变量注入，`models.json` 里写 `$PIGO_KEY_x` 引用，明文 Key 不落容器磁盘。文档确认 `apiKey` 支持 `"$NAME"`。预设 Provider 的环境变量名（`DEEPSEEK_API_KEY`、`MOONSHOT_API_KEY`、`MINIMAX_CN_API_KEY`、`ZAI_CODING_CN_API_KEY`）全部核实正确。
- pi 装到带版本号的 `--prefix`，通过软链切换，保留两个版本可回滚；配合 `pi-versions.json` 里的 `minSupported` / `recommended` / `blocked`，升级策略最完整。
- 安装验证包括用 `--no-session` 做一次 RPC 握手；考虑了 Android 12+ 的“幻影进程”限制。

缺点：
- MVP 范围膨胀：图片附件、`edit` 的 diff 视图、排队消息“立即发送”（需要 clear_queue 后重排）、平板双栏、冷启动 ≤ 3 秒都放进了第一期，真机一次走通的风险最高。
- 路线 A 直接下载 PiMet 的 `runtime-latest` rootfs：跨仓库耦合，而且据 B 的调查它派生自 DSH-Folk 的 release。`TarGzipExtractor` 同样原样搬。
- 启动命令有设计 bug（见下方）。

## 最终稿应从其他方案吸收的具体优点（以 B 为底稿）

1. **来自 C**：`:app/di/*Bindings.kt` 按工作流拆分文件，并设一个 `mvp/integration` 步骤，只负责把 Fake 切换成真实实现。这补上了 B 缺失的集成归属。
2. **来自 C**：Key 不落容器磁盘。Keystore 加密；自定义端点在 `models.json` 写 `$PIGO_KEY_<id>`，内置 Provider 用环境变量注入，用 C 核实过的变量名。B 的 auth.json 只设 600 权限，模型的 bash 工具照样能读到，这一点应当替换。
3. **来自 C**：pi 装到带版本号的 prefix、软链切换、保留最近 2 版回滚；`pi-versions.json` 带 `minSupported` / `recommended` / `blocked`；安装验证用 `pi --mode rpc --no-session` 加 `get_state` 握手。
4. **来自 A**：Ubuntu Base 用 `SHA256SUMS`、Node 用 `SHASUMS256.txt` 校验；换镜像时删 `.part`；空间预检；解压先到 staging 再原子重命名。
5. **来自 A**：启动时注入 `PI_OFFLINE=1`、`PI_SKIP_VERSION_CHECK=1`、`PI_TELEMETRY=0`（均已核实），缩短 PRoot 下的冷启动。
6. **来自 A**：会话删除改为移到 `sessions-trash/`；给出中文错误映射表（无网络、Key 错误、额度不足、模型不存在）；明确返回键行为（聊天页退到后台、安装向导先确认再中止）。
7. **来自 A**：停止 = 先 `clear_queue` 再 `abort`。依据 rpc-commands.md:128：“`abort` continues queued messages”，所以这个顺序是必需的，不是可选的。A 的乐观气泡（发送中 → 已排队/已发送 → 失败重试）也应写进 chat 验收。
8. **保留 B**：许可证重写清单、CI 禁止出现 `me.bmax.apatch`、WakeLock 只在运行中持有、会话扫描只读头尾 64KB。
