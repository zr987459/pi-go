## 4. 分项评审

### 4.1 终端形态还原度
- **C 最好**：`TermFormatter` 是纯函数，可以单测；把真 pi 在 80 列下的输出存成夹具，逐行比对，差异不超过 5%；关掉连字（`calt 0`），保证一字一格；用 `string-width` 的东亚宽度表；选择器底部的提示行直接变成可点的键帽，pi 的提示行本来就列出这些键；`hideThinkingBlock` 时只显示一行「Thinking…」；折叠文案沿用 pi 的「… N more lines (ctrl+o)」。
- **A 次之**：框线用 `drawBehind` 画，不拼制表符，中文混排时边框不会错位；双指缩放 10–18sp；对照 pi `footer.js` 做页脚快照；主题值的夹具来自在 node 里运行 pi 主题模块的输出。缺少「整屏输出逐行比对」。注意：A 的 R0 写「加入 JetBrains Mono 字体」，但 main 上已经有 `jetbrains_mono_*.ttf`，这一步多余。
- **B**：方向对，但只有 ASCII 线框和功能点，没有可量化的还原验收。

### 4.2 UI 形态是否极简好看
- **A**：色值、字号、8dp 网格、动效时长都写全了；用一个 ⌘ 面板兜住全部功能。模型胶囊、思考胶囊和上下文环单独占输入框上方一行，略显拥挤。
- **C**：配色表加形状规范；胶囊和上下文环收进输入框底栏，首屏更干净；只有三类动效，统一 180ms；删掉空会话的建议胶囊（`SuggestionText.kt`，pi 没有）。
- **B**：思路一致，但缺色板、字号这些可执行的视觉规格。
- **设置页**：用户原话是「设置里只保留配置模型」。**C 最贴合**：pi 的 `/settings` 是 pi 的一个功能，放进 ⌘「pi 设置」；设置页只有「模型」，并用仪器测试断言设置页根节点只有一个分组。A 和 B 在设置页底部挂「pi 设置」「关于与外观」或「高级」入口，A 还把网络代理放在模型页，与用户原话有轻微出入。

### 4.3 删除清单是否合理
三份都删了：吉祥物残留、汇率、文件浏览器和预览、Git 页、自动起名、每轮统计卡、dsh 视觉；都保留了：HTML/JSONL 导出（pi 有 `/export`）、附件和图片、草稿持久化、运行环境和前台服务；回收站都改成 5 秒撤销。没有发现误删 pi 原生功能。
- 有分歧的两项：
  1. **系统分享入口（Share Target）**：A 删，C 保留。pi 没有这个功能，但它是安卓上把图片或文件送进 App 的入口，不属于花活。**建议保留**，因为它只是附件的另一个来源，不新增界面。
  2. **`TurnStats` 的「本轮耗时」**：A 保留，理由是 pi 的 loader 上有计时，这个判断正确，应该合入。
- A 指出删除汇率与 11-03 调度决策 3 冲突，需要所有者确认。这一条很有价值，B 和 C 都没提。

### 4.4 工作流拆分
- **A**：R0 只加文件；R1–R4 只增不删，要删的类加 `@Deprecated`，用 grep 或 detekt 禁止新代码引用；R5 按模块分批提交删除，每一步都跑测试，PR 里列出全部删除路径；回收站里的会话先迁移回来。**删除安全性最好**。风险是 R5 同时负责删除、接线和总验收，是关键路径上的瓶颈。范围上，`feature/commands` 按目录切分（R1 数据层，R4 `ui/**`），可以接受。
- **C**：五条分支都写明独占的文件范围；r3/host 第一次推送限 ≤1 小时，只列接口、Fake 和全部动作 id，三条界面线随后就能并行；「先断引用再删文件」，`settings.gradle.kts` 里的 include 由 host 单独提一个小 PR；合入顺序写明。风险是 r3/host 的范围过大（contract、protocol、engine、workspace、chat 逻辑、commands、新模块 `core/session`、全部构建文件）。另有一处依赖方向问题：`PiActions.run` 在 `core/session`，却要打开 `feature/models` 提供的面板模型，需要用接口反转，或者把面板模型下沉到 contract。
- **B**：`r3/shared` 写了「`core/catalog` 与 `core/store` 中登录和凭据读写复用（只读调用）」，而 `core/store/**` 又整体归 `r3/models`，边界模糊；`r3/prune` 拥有 `core/ui`，但两种形态的 pi token 换算工具也放在 `core/ui`，等于删除线顺带承担新功能，容易产生冲突；终端线和极简线依赖的 `LineDiff`、树等逻辑由 prune 负责「下沉」，与 shared 的边界不清。

### 4.5 复用
三份都复用了引擎、协议、运行环境、W2 的服务商目录和 OAuth、W3 的附件和导出、W4 的扫描、索引、草稿、技能模板，以及 `Ansi`、`LineDiff`、`CompactionSummary`。A 和 C 还提到复用 W5 的 `PendingModel`（未配置的模型点进去配好后，自动回来选中），A 还复用了 `StreamingJankTest` 的慢帧门槛。复用程度上 A ≈ C > B。

## 5. 建议融合进最终稿的优点（以 C 为底稿）

**从 A 融合：**
1. **A §7.3 删除纪律**：R1–R4 只增不删，要删的类加 `@Deprecated("r3: 删除")`，用 grep 或 detekt 禁止新代码引用，删除按模块分批提交，每一步跑 `assembleDebug testDebugUnitTest`，PR 列出全部删除路径。与 C 的「属主删除、先断引用」叠加使用。
2. **A §7.3-4 用户数据迁移**：回收站取消前，一次性把里面的会话移回 `sessions/`，并提示「已恢复 N 个会话」。C 没写这一步，直接删会丢数据。
3. **A §5.3 `UiSession`**：除了 overlay 栈，还要保存**选择器里输了一半的搜索词**；`FormSwitchContractTest` 用反射断言 `ChatController` 的公开 API 里没有形态参数，切换形态时不发任何 RPC 命令（比对命令日志）。
4. **A §8.2 风险表中的三项实测**：`--no-session` 只能近似实现，界面上写明；`/trust` 在 RPC 模式下的行为由 R1 先实测，必要时启动参数加 `-a`；`settings.json` 与 pi 并发写时，用 `AuthJsonLock` 同款文件锁，只改目标键、保留未知键。
5. **A §2.12 `@文件` 展开格式**：读 pi 1.5.0 `interactive-mode` 源码确定格式，再做快照测试。C 只写了「路径引用」。
6. **A §8.2 汇率冲突**：在最终稿里列为「需所有者确认」，不要默默删掉。
7. **A §1.1 `TurnStats`「本轮耗时」保留**，供 loader 计时使用。
8. **A §2.1 `pi auth print-*` 的受保护入口**（二次确认、锁屏验证、60 秒清空剪贴板），可以作为 C 那条 Explain 的升级版，按 P2 处理。
9. **A §3.1 框线用 `drawBehind` 绘制，不拼制表符**，并支持双指缩放字号；**A §R2 页脚排版对照 `footer.js` 做快照**。
10. **A §4.3 生成中发送键三态**：输入框为空时显示 ■ 停止；有文字时显示「引导」；长按显示「排队 / 停止」。这解决了第 1 轮 Q4（有草稿时也能停止）。

**从 B 融合：**
11. **B §8 ★调整**：pi 设置页**按 `settings.json` 的 schema 生成控件**（开关、枚举、数字、字符串），不提供自由文本，降低写坏配置的风险。A 的 `PiSettingsSchema` 已经做到；再加 B 的单测「schema 覆盖清单 §8 的全部键」。
12. **B §3 ★调整**：`/quit` 在终端执行前先确认，避免误触杀掉正在生成的会话。
13. **B §8 风险 2 的退路**：桥接扩展失效时，退化为「读写文件 + 必要时重启引擎」，并在界面上说明。C 已经有类似表述，合并成一条即可。
14. **B §8 风险 1 的交付顺序**：先交付 UI 形态（用户日常用），再交付终端形态。可以作为合入顺序的参考。

**对 C 自身的修补：**
15. 拆小 r3/host，把 `core/workspace`（`@` 搜索、分支名）和 `pigo-bridge.ts` 拆成独立的子工作流，或者至少分 PR 提交，避免一条线成为瓶颈。
16. 解决 `PiActions.run` → `feature/models` 面板的依赖方向：面板模型（`OverlayModel` 子类）放在 `core/contract`，由 `feature/models` 通过 `AppGraph` 注入工厂。
17. 补上树的 `Ctrl+←/→` 折叠和展开、`Shift+T` 显示时间这两项在两种形态的明确入口，写进 `coverage-map.tsv`。
18. 保留系统分享入口（C 原本就保留），在 §1 写清楚它是「附件来源」，不是 pi 功能。

## 6. 最终

- **投票：C**
- **分数：A 8.5 / B 6.0 / C 9.0**
- **理由**：C 用「直接解析 `pi-features.md` 的覆盖测试 + 与形态无关的 `SessionHost`（草稿、overlay、阅读位置、形态）+ 三级切换验收」，把两条硬性要求变成了机器能核对的门槛，设置页也最贴合用户原话。建议吸收 A 的删除纪律、数据迁移、`UiSession` 和三项实测风险，以及 B 的按 schema 生成设置控件。
